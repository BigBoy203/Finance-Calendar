# Finance Calendar — web build

Personal bill / income / cash-flow tracker being grown into a full expense tracker with a wallet. Web only — there is no desktop/Electron build any more; the desktop *web* layout (sidebar) is kept working but is not the focus until mobile is finished. Plain-static React (no bundler, no JSX, `React.createElement` via `h`), deployed to Vercel at finance-calendar-web.vercel.app by pushing to this GitHub repo. Owner tests on a real iPhone in Safari and sends screenshots; mobile is the primary experience.

## CRITICAL BUILD RULES — follow exactly

The ONLY JS file that runs in the browser is `app.js`. The individual source files do nothing at runtime; they are concatenated into `app.js`. After editing ANY source file, rebuild:

```
cat app_core.js mobile.js ui.js entryform.js wizard.js quickadd.js home.js calendar.js overview.js spending.js wallet.js creditcards.js allbills.js settings.js > app.js
echo "" >> app.js
echo "ReactDOM.createRoot(document.getElementById('root')).render(React.createElement(App));" >> app.js
node --check app.js
```

- `storage.js` and `sync.js` load as separate script tags in `index.html` (before `app.js`) and define globals `window.api` and `Sync`. NEVER concatenate them into `app.js`.
- `sw.js` is the service worker (offline app-shell cache, network-first). It is standalone: never concatenated, never a script tag — `app_core.js` registers it as `sw.js?v=WEB_VERSION`, so bumping `WEB_VERSION` is what rolls the offline cache. Any new file the shell needs at runtime must be added to the `SHELL` list in `sw.js`. (`ui.js` and `wallet.js` are concatenated sources, not runtime files.)
- `index.html` loads only: vendor react, storage.js, sync.js, app.js — in that order. Vercel analytics is injected dynamically and ONLY on `*.vercel.app` hostnames, straight from the platform's own `/_vercel/insights/script.js`. The repo has no dependencies, no `package.json` and no build step — do not add one.
- After building, check for duplicate top-level definitions:
  `grep "^function \|^const " app.js | sed 's/(.*//' | sort | uniq -d` (must output nothing)
- `node --check` does NOT catch use-before-declaration (temporal dead zone). A `const` used by a useMemo above its declaration = black-screen crash at runtime. This has happened. When adding hooks/consts inside components, declare dependencies ABOVE their first use.
- After any CSS edit verify brace balance: count of `{` must equal `}`. Bulk python string-replace on styles.css has corrupted it before; prefer small targeted edits.
- Bump `WEB_VERSION` in `app_core.js` on every shipped change.
- Money math tests: `node .claude/skills/verify/wallet.test.js` (plain Node, no dependencies, runs against the built `app.js` with a frozen clock). Run it after touching wallet, advance, paid/covered, next-check or payment-plan code.
- Headless UI verification recipe (serve + Playwright at iPhone viewport + IndexedDB seed): `.claude/skills/verify/SKILL.md`.

## Code style — hard rules from the owner

- NO comments, labels, or explanatory notes anywhere in the code. None.
- No dead code. If a class/function loses its last caller, delete it AND its CSS.
- After UI changes, cross-check every `className:` used in JS against `styles.css` — nothing may render unstyled.
- Buttons and inputs must have visible borders (1px `var(--border-secondary)`); `--border-tertiary` is the hairline separator colour and is nearly invisible on dark backgrounds — do not use it for interactive controls. Rows inside a grouped list (`.entry-list`, `.switch-list`, `.action-list`) are the exception: the group is the affordance.
- Avoid an "AI look": no cramped rows of mixed controls, no boxed buttons floating right of text. Prefer full-width tappable rows (title + subtext + chevron), suggestion chips, clean 2-col grids with small uppercase labels.

## Design system (5.0)

- iOS-native look. Colours are tokens on `:root` / `[data-theme]` in `styles.css`: `--bg-page` (black in dark, `#f2f2f7` in light), `--bg-primary` cards, `--bg-sheet` / `--bg-cell` for sheets. Components never hard-code a surface — they use `--surface` (card or cell) and `--surface-2` (fill inside it). `.modal-content` re-points both to the sheet cell colours, so the same component looks right on a page and inside a sheet.
- Amounts use `font-variant-numeric: tabular-nums`. Section headings are `SectionHead` (`ui.js`: `.stats-title` 20px + `.stats-caption` + optional `right` node such as a `ChipToggle` or `.section-total`).
- Grouped lists: `.entry-list` (rows are `EntryRow`), `.switch-list` (rows are `SettingSwitch`), `.action-list` (rows are `ActionRow`), `.calc-list` (`.calc-row` label/amount lines with an optional `.total` or `.note`). Separators are inset hairlines drawn by `::before`. Inside a `.card` these groups go flush (no nested box).
- Mobile: `button { min-height: 44px }`. Any new small button-like element must be added to the exemption list (`min-height: 0`) at the bottom of the mobile media query or it balloons.

## Architecture / conventions

- All state lives in one JSON object persisted through `window.api` (IndexedDB, see `storage.js`). `persist(next, opts)` stamps `lastModified`. Data loaded through Sync is raw (not merged with defaults), so always guard new top-level keys: `(data.advances || [])`, `(data.wallet || {})`, `(data.paidAt || {})`.
- Paid state: `data.paidHistory["entryId|YYYY-MM-DD"] = true`, and `data.paidAt[key]` holds the timestamp it was marked (written by `togglePaidStatus`, the Add window and purchase edits; cleared on unmark / force-late / delete). Per-occurrence overrides in `data.overrides` keyed the same way. Partial payments: `data.covered[key]` plus `data.coverLog[key] = { amount, at }` written by `setCovered` — `togglePaidStatus` deletes `covered` but leaves `coverLog` so the wallet can tell a part payment made before a balance update from one after it.
- Recurrence end date: `entry.repeatUntil` (`''` = forever) caps `expandEntry`. In the Add window and `EntryFormModal` it is the "It stops on a date" switch, which reveals `RepeatEndBlock` (last-payment `DateField` + a 3/4/6/12 payment-count `ChipToggle` + an "N payments · $X in all" hint). The wizard still uses the inline "End repeat" `.setup-link`. `repeatLabel(entry, settings)` renders "monthly until Sep 19". Not to be confused with `useDateRange`/`dateEnd`, which is a bill that *spans* days on the calendar.
- Payment plans: `PAYMENT_PLAN = 'Payment plan'` is a subscription category (`MINOR_CATEGORIES`). Picking it turns the end date on automatically with a default count (`defaultPlanCount`: 4 for weekly/biweekly, 6 otherwise). An auto-chosen count follows frequency changes (`planEnd(date, freq, { auto: true })`); a count the user taps is kept (`{ count: n }`); typing a date clears it. `planProgress(data, entry)` gives `{ total, left }` and `scheduleLabel` shows "Next Oct 14 · 4 of 7 payments left" (or "Paid off").
- Lists of recurring things (Bills tab groups, Settings → income, Wallet purchases and activity) use `EntryRow` (`entryform.js`): colour swatch + name + subtext + amount + chevron, stacked inside one `.entry-list`. Without `onClick` it renders a static row with no chevron. Subtext comes from `scheduleLabel(entry, data)`, which shows the **next** due date via `nextDueDate(entry)` — never the entry's anchor/start date. Monthly figures for mixed frequencies go through `monthlyAmount(entry)`. Price ranges render through `fmtRange` (`$80–$140`, cents dropped only when whole).
- Deleting never happens in one tap. There are no `×` buttons on rows: delete is a `DeleteRow` (`ui.js`) at the bottom of the edit sheet that asks "Tap again to delete" first (`EntryFormModal` `onDelete`, credit-card sheet, purchase edit, advance edit, budget, "Remove this date").
- One-time entries (purchases and one-time income) are edited in the Add window itself: `QuickAddModal` takes `entry` for edit mode (type locked, "Save changes", delete row). `PriceOverrideModal` routes any advance occurrence (`occ.advanceId`) to `AdvanceSheet`, any one-time occurrence to `QuickAddModal`, and everything else to `OccurrenceHub`, which also has an "Edit <name>" row that opens `EntryFormModal` for the whole bill/subscription/income source.
- Month navigation on Home, Wallet/Spending, Statistics and the mobile calendar is the shared `MonthHeader` (`overview.js`): round chevron buttons and a "Today" pill whenever you are off the current month. Multi-option switches use `ChipToggle` (`wide` for a full-width segmented control — frequency, fee type, settings tabs, payment count); never a `<select>` inside a sheet. Boolean settings use `SettingSwitch` (`.switch-row` + `input.switch`) inside a `.switch-list`.
- Mobile detection: `useIsMobile()` (matchMedia ≤768px). Mobile UI: fixed shell with translucent header and tab bar, bottom tab bar Home · Overview · [＋ raised circle] · Wallet (or Spending when wallet tracking is off) · Bills; Settings is the gear in the header; Sync button top-left with "last synced" label under it.
- Modal rule: every dialog and form is a `Sheet` (`ui.js`) — never hand-roll `.modal-overlay` markup. `Sheet({ title, sub, head, onClose, foot, tall, className })` renders the overlay (dismissed through `useOverlayDismiss`), a head (title/sub or a custom `head` node, plus `CloseX`), a scrolling `.sheet-body` and an optional sticky `.sheet-foot` holding `.sheet-actions` full-width buttons. On mobile it is a bottom sheet: full width, rounded top, grabber, swipe down on the head to dismiss (`useSheetDismiss`), `tall` pins it to full height for forms so it doesn't jump as fields reveal. On desktop it is a centered window. Sheets can nest (the day sheet opens an occurrence sheet).
- Form field system: `Field({ label, hint })` = `.setup-field` (small uppercase label + full-width 46px input) inside `.setup-entry-grid` (2-col, `.single` for one). `AmountField` is the big bordered amount with the focus ring on the container. `ChipScroller` is a single horizontal row of category chips (edge-faded; pass `reveal` to scroll the selected chip into view when editing). `DateField` / `DateChips` show a formatted date (short weekday, year only when not this year) over an invisible real `<input type="date">`, so iOS still opens its native picker. `.setup-hint` is the small grey explainer. `.setup-field` label/input selectors are direct-child scoped (`>`) — keep them that way; `DateField` is a `div` for that reason.
- Mobile calendar: `.calm-*` classes; dot grid + compact daily totals, Month/Agenda `ChipToggle`, spanning range pills in a reserved lane below each week (lane-stacked when ranges overlap). The day detail is a `Sheet` (`DayDetailModal`) whose foot adds on the tapped day.
- Month math lives once in `useMonthFinancials(data, cursor)` (`overview.js`); `HomePage`, `StatisticsPage` and `SpendingPage` consume it. Advance inflows (`advanceInflows`) count as money in; advance paybacks are bill-like entries so they count as money out. `useNextCheck(data, period)` builds a pay-period window. Income landing today counts as already received, so checks are collected from tomorrow forward; `period` indexes into them. Period 0 runs today → next check and includes overdue via `getLateBills`; period n runs (check n-1, check n] with no overdue. Auto-repaid advances are kept out of the bill list and netted out of `checkAmount` instead (`takes` lists them for the card's note). `HomePage` owns the `period` state and the card's `‹ ›` nav (hidden unless more than one check is ahead).
- The Calendar tab is **Overview** (`page === 'overview'`, `OverviewPage`): a two-view tab switched by `OverviewSwitch`, which renders *in place of the mobile header title* (`MobileHeader` `titleEl` prop) and above the page on desktop. `view: 'calendar'` renders `CalendarPage`, `view: 'stats'` renders `StatisticsPage`: `CashFlowChart` (touch-scrubbable, today marker, live In/Out/Left legend), `CategoryDonut` (Out/In and By kind/By category chips; legend stacks under the donut on phones) and `GlanceGrid` tiles. The view state lives in `App()`.
- The Bills tab (`AllBillsPage`, `page === 'allbills'`) is the only place work piles up. `getAttentionItems(data)` merges `getLateBills` + `getNeedsAttention` into one deduped list (late first, then price-needed); `App` memoizes it as `attention` and its length drives the tab badge. There is no separate Late page — `attentionSummary()` writes the blue `.info-banner` copy from what is actually in the list, `.att-row` rows open `PriceOverrideModal`, and the list caps at `ATTENTION_PREVIEW` with a "Show all" toggle. Below it: filter chips and the recurring commitments in three groups that always render (`BILL_GROUPS`: essentials, subscriptions incl. payment plans, credit-card payments), each ending in an `.add-row` — "+ Add a bill" / "+ Add a subscription" open a new `EntryFormModal` right there (`_isNew`), the card group's row opens the Credit cards page (the only Bills sub-page, `MOBILE_SUBPAGES`). There are no separate Essentials/Subscriptions pages any more and the desktop sidebar has no Bills sub-list. One-time purchases and advances are never listed there.
- `OccurrenceHub` is the single hub for one occurrence: set the actual price, pay it from the next paycheck / pay part of it now (when opened from the next-paycheck card), mark paid, a three-state late row (marked late → clear / auto-late → dismiss / neither → mark late), edit the whole entry, and remove this date. `lateState(data, occ)` is the one place late/paid/dismissed is decided — use it, never re-derive it inline.
- Paycheck averaging is per income source: `entry.useAvgEstimate`, offered in the income form only when the source uses an amount range. `averagePaycheck(data, entry)` (WeakMap-cached on `data`) averages past occurrences that have a recorded amount; with two or more samples `expandAll` swaps the estimate into every **future** occurrence (`isEstimate`, shown as `≈$1,140` by `occAmountLabel`), so calendar totals, statistics, projections and the next-check card all move together. Settings → General shows the running average under the source.
- **Wording.** The owner wants the app readable by someone who has never seen it. Money that arrives on a schedule is a **paycheck** in the UI (never "check"); telling the app what you have is **Update balance** / "balance update" (never "wallet check"). Code names (`useNextCheck`, `nextCheck`, `data.wallet.checks`, `repayFromCheck`) keep their old names — only user-facing text changed.
- **Wallet** (`wallet.js`). `settings.walletEnabled` (default on; read through `walletOn(data)`) turns the Spending tab into the Wallet tab. `data.wallet = { checks: [{ id, at, date, amount, expected }], snoozed }`, newest first, capped at `BALANCE_HISTORY` — each entry is one balance update. The balance is derived, never stored: `walletSummary(data)` = last balance (`lastBalance`) + `walletMoves(data, check)`. Rules in `walletMoves` (tested in `wallet.test.js` — keep them in sync):
  - recurring paychecks and auto advance paybacks count when their date is after the check date and not in the future;
  - purchases count by their own date (a purchase *is* when money moved): after the check date, or on the check date only when `paidAt` is later than the check;
  - one-time income and advance inflows the same way, using `loggedAt` / `createdAt`;
  - bills, subscriptions, card payments and manual advance paybacks count when `paidAt` is later than the check, whatever their due date, minus any `coverLog` part payment made before the check; unpaid part payments count by `coverLog.at`.
  `recordBalance` stores what the app expected so the "Past balance updates" list can show how close it was. `balanceUpdateDue` (enabled + `walletMonthlyCheck` + no update this calendar month + not snoozed today) is only ever read by `SpendingPage` when it mounts: the balance question appears **only when the Wallet tab is opened**, never on Home or anywhere else, and never in onboarding. It opens `BalanceSheet` with `prompted` (and jumps the pager to Balance) — "Not now" snoozes for the day (`snoozeBalancePrompt`). iOS can't wake a web app, so "on the 1st" means the first Wallet visit on or after the 1st. The card's "Update balance" button opens the same sheet any time, and an "Update due" pill shows when a month has turned. Safe-to-spend on the card = balance − `useNextCheck(data, 0).due`, written as a sentence ("After the $X of bills due before your Oct 2 paycheck, you'll have $Y left").
- `resetSpendingHistory(data)` (Settings → Advanced → Start fresh, a two-tap `DeleteRow`) removes every purchase (`oneTimeKind === 'payment'`) plus their keys in every per-occurrence map, and clears `data.wallet` so the Wallet asks for a fresh balance. Bills, income, one-time income, budgets and advances stay. Covered by a test.
- **Advances** (`wallet.js`). `data.advances = [{ id, name, amount, date, createdAt, repayFromCheck, repayDate, feeType: 'none'|'flat'|'rate', fee, rate, rateBasis: 'once'|'apr' }]`. `advanceRepayDate` is the first paycheck strictly after the advance date when `repayFromCheck` (falls back to the stored `repayDate`), otherwise the chosen date. `advanceCost`: flat fee, rate × amount once, or APR prorated by days until payback. `getAdvanceEntries(data)` (WeakMap-cached) synthesizes one bill-like entry per advance — id `adv-<id>`, name "<name> payback", `autoRepay` — and is part of `getAllBillLikeEntries`, `buildEntryLookup` and `buildSourceListLookup` (`sourceList: 'advances'`). `isPaid` treats an auto payback as paid once its date arrives, so it is never late; manual paybacks can go late and are marked paid back from `AdvanceSheet`. Checklists render an "Auto" mark instead of a checkbox for `autoRepay` rows. Advances are logged from the Add window's type list or the Wallet card, and listed by `AdvancesSection` on the Wallet/Spending tab.
- The Wallet/Spending tab (`spending.js`, `SpendingPage`) is a swipe pager (`Pager`, `ui.js`): a full-width `ChipToggle` of page names over a horizontal scroll-snap strip (`.pager` / `.pager-page`), one page per screen, each page scrolling on its own. Tapping a name or swiping both work; the page index lives in `App` (`walletPage`) so it survives tab switches. `.app-shell > .main-content:has(.spend-page)` turns off the outer scroll and padding for this tab. Pages:
  - **Balance** (wallet on only): `WalletCard`, `WalletActivity` ("How your balance adds up" calc list, "What changed" moves, "Past balance updates"), `AdvancesSection`.
  - **Budget**: `MonthHeader`, hero = **left to spend** (`projected income − recurring bills − logged purchases`) with a per-day figure and a pace marker (`.spend-bar-pace`), "How this month adds up" calc list, budgets (`data.budgets = { [category]: monthlyAmount }`, day-to-day categories only, `BudgetModal`). Advances show here when the wallet is off.
  - **Spending**: `MonthHeader`, "Buy again" (`repeatBuys(data)` `.setup-chip`s passing a `preset` into `QuickAddModal`, current month only), **Where it went** (`.cat-row`, `categoryTotals`, `deltaNote` vs the previous month, tap to set `catFilter`), the month's purchases as `EntryRow`s.
  - **Trends**: `MonthHeader`, six-month bar chart, four stat tiles.
  Each page states one big number at most — keep it that way; the owner found the old single scroll full of competing big figures confusing.
- A logged purchase is money already spent: `QuickAddModal` marks one-time payments dated today or earlier as paid on save (with a `paidAt` stamp), `oneTimeOccurrence` stamps `isOneTime`, and `getLateBills`/`getNeedsAttention`/`lateState` never treat a one-time payment as late. Don't reintroduce that — it filled the attention list with things the owner had already paid for.
- Home is bill-first: full-bleed gradient hero (`.home-wash`, no card box) showing only "So far this month" (money in minus money paid out — there is no "Projected" figure; the Budget page owns the month forecast), the "Before your next paycheck" card (more than `OVERDUE_FOLD` overdue bills collapse into one `.overdue-fold` row so upcoming bills stay visible; the checklist runs flush inside the card), and a collapsible "Bills this month" row (`.drop-card`) with the covered/left progress bar. No charts on Home.
- Onboarding (`wizard.js`): welcome screen → income → bills → subscriptions → credit cards (4 steps). Bills/subs start EMPTY with tap-to-add suggestion chips. Mid-month rule: on the final step (if today > 1st) a default-on switch marks already-passed bills this month as paid so nothing shows falsely late on day one. There is no wallet step: the Wallet tab asks for the first balance the first time it is opened.
- Things that exist in exactly one place (don't re-add duplicates): sync lives in the header/sidebar button (`SyncModal`), not in Settings; the month's in/out forecast lives on Wallet → Budget, not on Home or Statistics; upcoming bills live on Home's next-paycheck card and the calendar, not Statistics; balance updates live on the Wallet tab, not Settings.
- Add window (`quickadd.js`) is the most-used screen and is built for speed. It is a tall `Sheet`: the head is the type button (emoji + type + "Tap to change") that swaps the body for a `TypeList` of Purchase · Bill · Subscription · Income · Advance. Body: big autofocused `AmountField`, category `ChipScroller`, an **optional** name that falls back to the category, Today/Yesterday/Other-day `DateChips` (a `DateField` for recurring types), a frequency `ChipToggle`, then a `.switch-list` of extras that reveal fields below it: "Already paid for" (purchases, defaults to on for today or earlier), "The amount varies", "It stops on a date" / "It ends after the last payment", "It spans several days". The advance type renders `AdvanceFields` from `useAdvanceForm`, the same hook `AdvanceSheet` uses for editing. The single foot button is disabled until there is an amount and says so ("Enter an amount") — never fail silently, that was a real bug. There is deliberately no `<select>` in this window. Category lists: `MAJOR_CATEGORIES` (bills) and `MINOR_CATEGORIES` (subs, incl. Payment plan) are recurring-bill shaped; `ONE_TIME_PAYMENT_CATEGORIES` is day-to-day spending (Groceries, Food & drink, Gas, …) — keep bill-shaped names out of it, and `categoriesByUse` floats the ones this person actually buys to the front.
- Haptics: `haptic('light|medium|success|warn|heavy')` helper; respects `settings.hapticsEnabled`. iOS Safari does not support web vibration — that's expected, don't "fix" it.

## iOS hard limits (do not fight these)

- No background tasks, no notifications, no silent filesystem writes, no auto-folder creation from a web app. One-tap share-sheet export is the floor on iPhone. Anything "scheduled" (the monthly balance question, the Monday backup reminder) happens on the next app open (for the balance question, the next time the Wallet tab is opened).
- iOS opens a **wheel picker** for `<select>` and `<input type="date">`, which shrinks `visualViewport` exactly like a keyboard does. `index.html` must only treat that shrink as `--kb` (and only scroll a field into view) when the focused element is a real typing field — `isTypingField()`. Counting the picker as a keyboard re-lays-out the modal mid-tap, so the next tap lands on whatever moved under the finger. This caused a real "can't change the category, it hits the buttons below or closes the window" bug; don't undo it. `index.html` also sets `--sheet-safe` to 0 while the keyboard is up so sheet feet don't keep the home-indicator padding above the keyboard.
- Overlay taps go through `useOverlayDismiss(onClose)`, which only closes when the pointer went **down** and **up** on the overlay itself. Never dismiss on a bare `onClick` target check — a dismissed picker fires a click that closes the modal. Only call it from a component that is actually showing an overlay (it locks page scroll while mounted) — `Sheet` does this for you.
- File inputs MUST be attached to the DOM (`document.body.appendChild`) or iOS never fires `change`. No focus-based cancel timeouts — iOS loses the race. Both are already handled in `storage.js` and `sync.js`; keep it that way.
- apple-touch-icon must be PNG (`assets/icon-180.png`), regenerated from `assets/icon.svg`.

## Roadmap (owner's stated priorities)

Wallet tracking, advances and payment plans shipped in 5.0 along with the iOS-style redesign. 5.1 renamed "check" to "paycheck" throughout, moved the balance question to the Wallet tab only, turned the Wallet tab into a four-page swipe pager, added "Reset spending history", and removed duplicated features. Still open: turning `repeatBuys` into a real prediction — it already knows the average gap between purchases, so it can say what is due to be bought again rather than only offering a re-log chip. The desktop *web* layout is maintained but gets its own pass only once mobile is where the owner wants it. Always flag honest difficulty and scope concerns BEFORE building, not midway.
